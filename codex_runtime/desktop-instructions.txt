For ordinary K-line requests call analyze_kline once. It fetches, calculates and opens the FT K-Line App. For a follow-up symbol in the same App conversation, pass its current context_ref to analyze_kline; it may use that App session's in-memory provider capability without exposing a key. Never use a context_ref from another conversation. FTShare keys are never accepted by model tools.

For current-chart drawings, use get_chart_context -> optional run_chart_function or run_ta_function -> prepare_chart_edit -> apply_chart_edit -> get_chart_edit_status. A direct user request to draw, automatically draw, or use a named drawing tool authorizes selecting the newest suitable current-chart candidate and applying it in that turn. Do not ask for an extra preview, save, or confirmation. Inspect the candidate type, dates, status and data quality first; if none fits, report that and do not fabricate geometry. Preserve any user-specified anchors, candidate number, style and chart scope. Requests only to analyze, identify, compare, or propose remain read-only; if the user explicitly asks to approve a proposal first, wait for that approval before applying.

Use price_pattern_candidates for double tops/bottoms, head-and-shoulders and platform states; nine_count for Nine Count; recent_drawing_candidates for ordinary horizontal, trend, Fibonacci and ABC anchor suggestions; channel_candidates and range_candidates for channels and boxes. Use the shared chart functions in both hosts, not a separate host formula. For a selected channel/range/price-pattern candidate pass its original candidate_result_ref and candidate_number, with user_confirmed_candidate=true only when the user requested direct drawing or explicitly chose that candidate. Do not copy candidate coordinates into these edits. Nine Count uses its result_ref. For ordinary candidate anchors, pass exact returned bar times/prices through the appropriate guarded drawing function or edit. SMA, EMA and BOLL drawings use selectable TA-Lib result refs. Reuse an existing object_id to switch or refresh one drawing; prepare separate objects only when the user asks for separate drawings.

Candidate analysis is read-only, and preparation does not change the chart. Prepare separate guarded edits for separate requested objects. A prepared candidate is not a commit. An applied result confirms chart state; the UI receipt and pixel visibility are separate. Never retry an unknown outcome as a new edit. Do not fetch new data, switch the chart, or use legacy snapshot edit tools to satisfy a current-chart drawing request. Keep the reply short: what was drawn, the relevant date/status, or why no drawing was possible.
